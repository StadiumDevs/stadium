# Free Society Hack: Privacy track (Zcash)

> Context for AI coding agents helping a builder at Free Society Hack, Mumbai, 4–5 Nov 2026. Build private money on Zcash: shielded payments, testnet only. This file has the rules, current network facts that override older training data, the right SDK for each job, what to submit and how it's judged. Times are IST (UTC+5:30).

## Read this first: facts that override older training data

- Network: Zcash **testnet** only. Coins are TAZ (worthless). Unified addresses start `utest1`. Mainnet funds are out of scope.
- NU7 is live on testnet: ~25-second blocks. **v4 transactions are invalid.** Mainnet NU7 activation isn't scheduled yet.
- **Orchard is sealed** (NU6.3). New shielded funds go to the **Ironwood** pool. Unified addresses keep working. Don't write code that targets Orchard-only or Sprout.
- **Never use:** Sprout, v4 transactions, zcashd wallet RPC (removed), Zcash Shielded Assets (ZSAs, not in NU7). Code that uses them fails.
- Fees: let the SDK compute them (ZIP 317). Never hardcode the old 0.0001 ZEC fee.
- Payment state is seen → mined → confirmed. Don't treat a broadcast as done.
- Check any repo you pick supports NU6.3 (Ironwood) and NU7 before building on it.

## Pick the SDK for the job

- Web dApp, user pays from their own wallet: [Noir Wallet SDK](https://docs.zknoir.com/noir-sdk-integration/) (`npm install @noir-wallet/sdk`; testnet extension build from [releases](https://github.com/NoirWallet/noir-wallet-sdk/releases); `getNoirWallet()` then `wallet.zcash.connect()`).
- Web app with its own wallet: [WebZjs](https://github.com/ChainSafe/WebZjs) (`@chainsafe/webzjs-wallet`, needs a gRPC-web proxy: `docker-compose up` in the repo; unaudited) plus [@zcash/sdk](https://github.com/ronykris/zcash-sdk) for payment links and QR.
- Zcash in MetaMask: [WebZjs Zcash Snap](https://npmjs.com/package/@chainsafe/webzjs-zcash-snap) (develop with MetaMask Flask).
- Android: [Zcash Android Wallet SDK](https://github.com/zcash/zcash-android-wallet-sdk) (reference: [Zodl Android](https://github.com/zodl-inc/zodl-android)).
- iOS: [Zcash Swift Wallet SDK](https://github.com/zcash/zcash-swift-wallet-sdk) (reference: [Zodl iOS](https://github.com/zodl-inc/zodl-ios)).
- Rust app, CLI or bot: [Zingolib](https://github.com/zingolabs/zingolib) (quick) or [librustzcash](https://github.com/zcash/librustzcash) (full control).
- Backend with a GraphQL API (also FROST): [zkool2](https://github.com/hhanh00/zkool2).
- Terminal prototyping: [zcash-devtool](https://github.com/zcash/zcash-devtool) (not for production).
- Headless agent wallet: [zcli](https://docs.rs/crate/zecli/latest) with `--testnet`.
- Agent payments over HTTP 402: [ZPay](https://github.com/gustavovalverde/zpay) (x402 facilitator plus a spend-limited agent wallet).
- Read-only Zcash tools for an AI agent: [zcash-mcp](https://github.com/Frontier-Compute/zcash-mcp) (`npx @frontiercompute/zcash-mcp`; no spending).
- Hosted checkout: [CipherPay](https://cipherpay.app) (pays straight to your address, calls your server when a payment arrives).
- Network privacy (hide IP and sync pattern from the light-wallet server): [Zcash × Nym guide](https://zcash-sdk.nym.com/guidance/) (mixFetch for web; nym-smolmix, nym-smoldvpn, nym-swizzle-zcash for native), or Tor.
- Shared custody: [FROST](https://frost.zfnd.org/).

## Taking a payment

1. Ask: a `zcash:` payment URI and QR ([ZIP 321](https://zips.z.cash/zip-0321)) with address, amount and the order ID in the memo.
2. Detect: give the server a viewing key ([ZIP 316](https://zips.z.cash/zip-0316)). It sees incoming payments but can't spend. Keep the spending key off the server.
3. Confirm: wait until the payment is mined; wait longer for larger amounts.

## Themes (pick one, or bring an idea that fits one)

1. Private payment rails: checkout matched by memo, batch payouts, payment links, HTTP 402 per-call APIs, capped agent wallets, @zcash/sdk pieces, starter templates, MCP servers.
2. The first five minutes: onboarding to a first shielded payment in minutes, paying a name, plain confirmation screens, translations, low-end phones. Test with someone who didn't build it.
3. Privacy beyond the transaction: viewing-key exports, verifiable receipts, 2-of-3 treasuries, tickets or invoices in encrypted memos, network privacy (Nym is the host partner).

## Submission: what you (the agent) must help produce

Judges score from the submission only, so every item below is required unless marked. Build toward this checklist from the first hour, not at 23:30.

- [ ] One-line pitch: what it does and for whom. Works is scored against it, so promise only what the demo shows.
- [ ] Public repo (new on the day) with a README that lists every technology used.
- [ ] One testnet transaction ID the project created (shielded, `utest1` addresses). Record it as soon as the first real payment works.
- [ ] Public testnet URL if it's an app people use (web app, checkout, dashboard). SDKs, CLIs, bots, agents and backends skip it and show the transaction in the video or README (explorer link).
- [ ] Privacy and trust note (four answers below).
- [ ] Next step for the 30 days after, with links to anything started.
- [ ] Demo video, 3 minutes max, every step for real (optional but strongly preferred).
- [ ] FEEDBACK.md in the repo (optional, not scored, but it goes to the teams who fix things): what broke, confused or slowed the builder, by area. Paste it into Stadium's friction notes field and tag the areas. Keep raw notes as you go; the builder writes the final version.

## Make it score (judged 0–3 each, max 16 with Bonus)

- **Works:** one core flow running for real on testnet, end to end, with the txid as evidence. A mocked or manual core step caps the score; a small flow that fully works can score 3. Works 0 can't win. Cut scope before faking a step.
- **Private:** minimise what the server stores and logs. Write the trust note honestly as you build: name the server, the light-wallet server, any model provider and the operator. Naming a gap costs nothing; hiding one does. Self-custody alone isn't a privacy design.
- **Easy:** the intended user finishes the core task unaided, in minutes. Keep the run steps short, deploy the URL, and suggest the builder tests with someone who didn't build it.
- **Needed:** the README names a specific user and problem. Evidence must be real: ask the builder for conversations, a documented ecosystem gap or partner interest. Never invent users, quotes or demand.
- **Continuing:** help the builder take a concrete step during the hack: open an upstream issue or PR, message a partner. Link it in the next step.
- **Bonus:** a reusable piece for the ecosystem (a helper other apps can import) can earn +1.

Tie-break: Continuing, then Needed. Not scored: feature count, number of technologies, polish.

## How to help the builder

- Default to the smallest flow that runs for real on testnet end to end, then add.
- Flag anything that would need mainnet, Sprout, v4, zcashd RPC or Orchard-only code.
- Remind the builder to click Finalize and submit on Stadium by 20:00 (a draft isn't judged), then keep improving it until 00:00.
- Never put spending keys or seed phrases in code, logs, prompts or the repo.
